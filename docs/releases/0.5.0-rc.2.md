# 0.5.0-rc.2 release notes (prepared, not published)

This release candidate aligns the SDK with the public API contract at docs
revision `b171ff0a408bbeb024535941b83b861d205a829f`, including the changes since
`a52ce19`. The source baseline is develop commit
`39fa334cb879ee5b8791f74d62c4ac1ddcd2fc22`.

## Changes

- Validate nonempty Collection schemas, metadata tag values, PATCH no-op/clear
  semantics, and mutually exclusive document delete selectors.
- Reject unsupported JSON request fields and explicitly send the bulk import
  content type.
- Return concrete Gateway error classes for HTTP 409/413/502/503/504, expose
  `Retry-After`, and declare the mapped classes in public operation error unions
  and standalone function signatures.
- Clarify default-Branch statistics, read consistency, pagination, and signed
  upload behavior; add ESM/CJS error declaration regression checks.

## Migration

See [CHANGELOG](../../CHANGELOG.md) for RC1-to-RC2 migration guidance and the
cumulative breaking changes from stable 0.4.3. In particular, replace empty
schemas, supply exactly one delete selector, remove unsupported request fields,
and update exact error-class checks. Existing `instanceof LambdaDBError`
handling remains valid. Branches and Tags are Collection-scoped; they do not
replace cross-Collection source cloning.

## Publication plan

After review, main merge verification, and explicit publication approval:

- Tag the reviewed main commit as `v0.5.0-rc.2`.
- Create a GitHub prerelease with latest disabled.
- Let the existing release workflow publish the tested tarball with npm
  dist-tag `rc`, Trusted Publishing, and provenance.
- Verify `latest=0.4.3`, `rc=0.5.0-rc.2`, exact-version installation, integrity,
  provenance, and GitHub prerelease status.

After publication, install explicitly with
`npm install @functional-systems/lambdadb@0.5.0-rc.2`.

The contract revision identifies the SDK source contract, not the deployed
service revision or general availability. Environment smoke results and exact
tested SDK commits are recorded in the release preparation PR; deployment
revision evidence must be confirmed before publication.
