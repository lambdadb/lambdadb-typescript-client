# 0.5.0 release notes

This stable release adds Collection-scoped Data Versioning and incorporates
RC1–RC3 feedback plus the Branch source and parent metadata update from
[server #405](https://github.com/lambdadb/lambdadb/pull/405).
The public API contract is pinned to
[`c44180406c05b1a9043d8516e7c7f60df91fc9a7`](https://github.com/lambdadb/docs/blob/c44180406c05b1a9043d8516e7c7f60df91fc9a7/reference/api/openapi.json).

## Changes

- Create, list, and delete Branches, Tags, and Aliases, and retarget Aliases.
  Lifecycle methods expose Promise-based ordinary and `*Safe` paths.
- Select Branch, Tag, or Alias refs for Query, Fetch, and paginated document
  reads. Select a Branch for document writes and bulk uploads. Ref selectors
  are preserved on every page; an immutable Tag provides a stable export.
- Create Branches only from Branch sources in the same Collection. Omit source
  to use `main`, or use `branchSource(name, asOf)` for a retained point-in-time
  snapshot. Tag creation continues to accept Branch or Tag sources.
- Branch create/list responses expose required nullable `parentBranch`,
  `headSnapshot`, and `parentSnapshot`. `parentBranch: { branchId, name }`
  identifies the direct source even for an empty head or an ancestor snapshot.
  It is null for main or when no parent was recorded. This historical identity
  survives parent deletion/name reuse and does not prevent parent deletion.
- `parentSnapshot` is fixed fork metadata, not the previous head; it remains
  null for main and Branches created from empty sources. Tag responses retain
  non-null top-level `snapshotId` and `snapshotCommittedAt` fields.
- Expose Collection description, metadata tags, default Branch, and snapshot
  retention. Add concrete conflict, payload-size, and gateway errors, plus
  optional `retryAfter` response metadata.
- Forward server-signed bulk-upload headers and preserve the upload-info type.
  A separate transfer client handles uploads and out-of-line downloads without
  sending project API credentials to presigned URLs.

## Migration from stable 0.4.3

- Collection creation requires a nonempty `indexConfigs` map. Removed
  cross-Collection source-cloning fields have no direct replacement; Data
  Versioning operates within one Collection. Removed response fields include
  `sourceProjectName`, `sourceCollectionName`, `sourceCollectionVersionId`, and
  `collectionStatus`.
- Collection creation returns create metadata rather than a full Collection
  description. Create/delete success statuses are now 201/200. Update returns
  Collection timestamps as Dates, consistent with create/get/list.
- Wire timestamps use Unix milliseconds. The collection-scoped facade returns
  Dates, including nested snapshot commit times. Update response mocks to the
  current required fields and timestamp units.
- Collection PATCH requires at least one non-null field. Omitted or null fields
  retain existing values; `tags: {}` clears tags and an empty description clears
  the description. Supplied tags replace the map and cannot contain blank values.
  Schema additions at any object depth must preserve existing fields/settings.
- Document deletion requires exactly one of `ids` or `filter`;
  `partitionFilter` only narrows that selection. Unsupported request-body fields
  fail validation instead of being silently removed.
- Query/Fetch allow `consistentRead: true` only for implicit main or a direct
  Branch. List reads committed data. Pending bulk imports are not included in
  the consistent-read overlay.
- Bulk upload-info responses must include `type`, `httpMethod`, `sizeLimitBytes`,
  and signed `headers`. Low-level completion `type` is optional; omission stays
  omitted. Automatic upload/completion preserves the server-returned metadata.
- Referenced Branch/Tag deletion returns `CatalogConflictError` (409); delete
  or retarget referencing Aliases first. Update error handling for the concrete
  conflict, payload-size, and gateway classes; `LambdaDBError` remains a base.

## Migration from release candidates

RC3 users must replace Tag sources used to create Branches with the intended
Branch source and include required nullable `parentBranch` in response mocks.
There is no synchronous network API; synchronous ref/source helpers remain.

Earlier RC users must also replace `RefDetails` with `BranchDetails` or
`TagDetails`, and replace Branch `snapshotId` access with
`branch.headSnapshot?.snapshotId`. Include both nullable Branch snapshot fields
and the required Tag `snapshotCommittedAt` field. See the
[cumulative changelog](../../CHANGELOG.md) for RC-specific validation changes.

npm install @functional-systems/lambdadb@0.5.0
