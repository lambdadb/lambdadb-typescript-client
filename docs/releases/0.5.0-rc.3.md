# 0.5.0-rc.3 release notes (prepared, not published)

This release candidate supports the updated Branch and Tag snapshot responses
in the [pinned OpenAPI contract](https://github.com/lambdadb/docs/blob/c8495bf47cd8918cfd546b4742823fd4cf3d0814/reference/api/openapi.json)
at `c8495bf47cd8918cfd546b4742823fd4cf3d0814`. The reviewed contract range is
`b171ff0..c8495bf`; the source baseline is develop commit
`b2364b477a3a44c41c54d84126b2a453d8525add` (PR #22).

## Changes

- Branch responses expose `headSnapshot` and fixed `parentSnapshot` objects.
  Both fields are required and nullable. Parent metadata describes the fork
  snapshot and does not extend snapshot retention.
- Tag responses retain a non-null `snapshotId` and add `snapshotCommittedAt`.
  The collection-scoped client converts creation and snapshot commit timestamps
  to `Date`, including nested Branch timestamps; wire models retain numeric
  Unix milliseconds.
- Low-level bulk completion accepts an optional string `type` and preserves
  omission. Automatic bulk uploads retain the required
  `Content-Type: application/json`, server-returned signed headers, and the
  upload-info type in the completion body.
- Schema-update guidance now allows new children at any object depth while
  preserving all existing fields and settings. Existing serialization already
  supports these additions.
- Referenced Branch/Tag deletion returns `CatalogConflictError` (409). Delete
  or retarget all referencing Aliases before retrying. Existing error mapping
  and default no-retry behavior for 409 are preserved.
- Query and Fetch continue to allow `consistentRead: true` only for direct
  Branch refs or an omitted ref (implicit main). List has no consistent-read
  option. Live smoke tests now allow five minutes for each committed-data phase.
- Development-only dependency resolutions include the reviewed updates from
  PR #21. Runtime dependency requirements are unchanged.
- Correct the Collection listing example to use `ListCollectionsResponseWithDates`,
  matching the collection-scoped client.

## Migration from RC2

- Replace `RefDetails` with `BranchDetails` or `TagDetails`.
- Replace `branch.snapshotId` with `branch.headSnapshot?.snapshotId`. Check for
  a null head before using it. `parentSnapshot` stays fixed as the head advances;
  it remains null for main and branches created from an empty source.
- Update response mocks to include both Branch snapshot fields and the Tag
  `snapshotCommittedAt` field. Tag snapshot identity cannot be null.
- A low-level `bulkUpsert` completion no longer inserts `type` when omitted.
  Supplying completion metadata does not replace the required upload header.
- For migration from stable 0.4.3, also apply the cumulative breaking changes
  in [CHANGELOG](../../CHANGELOG.md).

## Publication plan

After review, main merge verification, and explicit publication approval:

1. Confirm the reviewed release commit is on main and verify the target API
   deployment evidence and applicable smoke results.
2. Tag that main commit as `v0.5.0-rc.3`.
3. Create a GitHub prerelease with latest disabled. The existing workflow
   publishes the tested tarball with npm dist-tag `rc`, Trusted Publishing,
   and provenance.
4. Verify exact-version installation, integrity, provenance, GitHub prerelease
   status, `rc=0.5.0-rc.3`, and unchanged stable `latest=0.4.3`.
5. Synchronize main back into develop while preserving release ancestry.

After publication, install explicitly with:

```bash
npm install @functional-systems/lambdadb@0.5.0-rc.3
```

The contract revision identifies the source contract, not a deployed service
revision or general availability. Exact tested SDK commits and environment
smoke results are recorded in the release preparation PR. Registry and tag
availability must be rechecked immediately before publication.
